## 1. 三层关系总览

| 层 | 角色 | 配置命名空间 | 关键代码 / 文档路径 |
|---|---|---|---|
| **AHP 协议** | 会话服务器 ↔ 多客户端的 JSON-RPC 线协议；Telemetry Channel 承载 OTLP/JSON | —（协议层） | `src/types/`（wire types）；`reference/otlp.html`（规范） |
| **Agent Host OTel** | 独立 utility 进程，承载 Copilot / Claude / Codex native runtime | `chat.agentHost.otel.*` | `src/vs/platform/agentHost/`；`node/otel/agentHostOTelService.ts` |
| **Copilot Chat OTel** | 扩展宿主内 Local Copilot Chat 的前台 / 内联 / CLI 包装器 | `github.copilot.chat.otel.*` | `extensions/copilot/src/platform/otel/`；`extensions/copilot/docs/monitoring/` |

**一句话区分**：AHP 定义“**怎么传**”（OTLP/JSON 薄透传）；Agent Host OTel 决定“**Agent Host 会话产生哪些信号、怎么路由和持久化**”；Copilot Chat OTel 负责“**扩展宿主内前台聊天的完整遥测**”。


> **实测校准（2026-11-06）**：本文档结论已用本机两份离线库对照核对——
> `agent-host-traces.db`（12588 span / 229 键 / 5962 事件 / 26 MB / `captureContent=false`）与
> `agent-traces.db`（3285 span / 60 键 / 21 事件 / **3.63 GB** / `captureContent=true`）。
> 标注 **“实测：”** 的句子来自落库数据，与官方文档冲突时以实测为准。三处被推翻的结论：
> **① 扩展库路径不是 `otel/spans.db` 而是 `agent-traces.db`；② Agent Host 不发任何 cache token；③ `execute_hook` span 两条管线都不存在，hook 走 `span_events`。**
> 详见两份管道文档的“实测附录”（Copilot Chat 第 20 节、Agent Host 第 19 节）。


## 2. AHP 协议层：Telemetry Channel

> **本次实测未覆盖本节**：AHP 是在线 JSON-RPC 通道，两份离线 SQLite 库都不含其数据，因此第 2 节保持官方文档原文、未做校准。
> 与实测数据可交叉验证的一点：**Telemetry 通道无状态、不重放历史**，所以历史统计必须依赖 SQLite/AHP 之外的持久化——这与本项目“变更驱动快照 + 本地库为准”的设计一致。

### 2.1 定位与 Channel 模型

AHP 的 Telemetry Channel 是**无状态通道**，将 agent host 的 OpenTelemetry logs、traces 和 metrics 以 **OTLP/JSON payload** 推送给已订阅的客户端。**每一条命令和通知的 `params` 都携带顶层 `channel` URI**，中间代理可仅凭 `(method, params.channel)` 分发消息。

**关键 Channel URI 方案**：

| URI | 状态 | 说明 |
|---|---|---|
| `ahp-otlp:` | **无状态** | OTLP logs / traces / metrics；具体 URI 在 `InitializeResult.telemetry` 中声明，客户端须视为**不透明**（opaque），仅展开协议定义的模板变量 |
| `ahp-root://` | 有状态 | 全局状态，始终存在 |
| `ahp-session:/<uuid>` / `ahp-chat:/<id>` | 有状态 | 会话 / chat 级状态 |

### 2.2 TelemetryCapabilities 与发现

`TelemetryCapabilities` 定义在 `InitializeResult.telemetry` 中，三个字段均**可选**：`logs`、`traces`、`metrics`。字段存在时，值可以是字面 URI，也可以是 **RFC 6570 URI 模板**；**缺失字段表示 host 不发出该信号**。

**`logs` 通道的模板变量**：协议目前只定义了 `{level}`（最小 OTLP SeverityNumber 短名：`trace`、`debug`、`info`、`warn`、`error`、`fatal`）。Host **SHOULD** 遵守展开后的 `{level}`；客户端 **MUST** 仍做防御性过滤。未声明 `{level}` 的 host 发送所有严重级别。**`traces` 和 `metrics` 不定义任何模板变量**。

### 2.3 通知方法

| 方法 | Channel | Payload |
|---|---|---|
| `otlp/exportLogs` | `TelemetryCapabilities.logs` | OTLP/JSON `ExportLogsServiceRequest` |
| `otlp/exportTraces` | `TelemetryCapabilities.traces` | OTLP/JSON `ExportTraceServiceRequest` |
| `otlp/exportMetrics` | `TelemetryCapabilities.metrics` | OTLP/JSON `ExportMetricsServiceRequest` |

Payload 直接引用 `opentelemetry-proto` 的线格式，AHP **不重新定义** OTel 数据模型。

### 2.4 稳定性与 SDK 实现位置

Telemetry 通道稳定性为 **2 - Stable**，协议层面的通知方法名、Payload 格式和 Channel URI 语义有明确的兼容性保证。

在 `microsoft/agent-host-protocol` 仓库中，Telemetry **没有独立的“Telemetry 模块”**，完全复用 AHP 的通用 Channel 抽象：

- **Wire Types**：`src/types/` 下定义 `TelemetryCapabilities`、`otlp/export*` 方法名和 Payload 类型。
- **Client**：`AhpClient`、`Subscription` 不包含 Telemetry 专用逻辑；Telemetry 作为无状态通道，订阅返回空快照，之后的事件以 `notification` 类型推送。
- **Host 侧实现**：将 `otlp/export*` 转发到 collector 或写入 SQLite 的逻辑属于 Host（如 VS Code 的 `IAgentHostOTelService`），**不在协议 SDK 内**。


## 3. Agent Host OTel 管道

### 3.1 定位与独立性

Agent Host 是**独立 utility 进程**（`src/vs/platform/agentHost/`），嵌入 native `@github/copilot-sdk` runtime，而不是使用扩展宿主的 in-process 工具调用循环。它拥有**自己的 OTel 管道**，使 native-SDK 会话的 traces 可导出到 collector 或本地持久化。**可用性：Insiders / 非 stable 构建**，需要 `chat.agentHost.enabled = true`。

**与 Copilot Chat 管道的硬性隔离**（官方文档明确警告不要合并或假设一个设置会配置另一个）：

| 属性 | Agent Host OTel | Extension OTel |
|---|---|---|
| 进程 | 独立 utility 进程（`src/vs/platform/agentHost/node/`） | 扩展宿主 |
| 配置前缀 | `chat.agentHost.otel.*` | `github.copilot.chat.otel.*` |
| 服务接口 | `IAgentHostOTelService`（`node/otel/agentHostOTelService.ts`） | `IOTelService`（`extensions/copilot/src/platform/otel/`） |
| SDK | `@github/copilot-sdk` `TelemetryConfig` | `@opentelemetry/sdk-node` 直接使用 |
| 持久化 | `<userData>/agent-host/otel/agent-host-traces.db` | `<extensionGlobalStorage>/agent-traces.db`（**实测**；旧文档误写 `otel/spans.db`，实际不在 `otel/` 子目录、文件名也不是 `spans.db`） |
| **实测：trace 形态** | 深树（2175 个 `chat` 只分布在 15 个 trace） | 几乎全平（3275/3285 独立根 trace，仅子代理链路成树） |
| **实测：resource attributes** | 以 **span attribute** 落库（`service.namespace` 全覆盖 12588） | **不落库**，离线无法判定 `service.name`/`session.id` |
| **实测：span_events** | 5962 条（hook/sandbox/usage_info/exception） | 21 条（exception/turn_start/turn_end/user_message/tools_available） |

### 3.2 两种运行模式

**Pass-through 模式**  
触发：`chat.agentHost.otel.enabled = true` **且** `dbSpanExporter.enabled = false`。  
SDK 直接导出到用户配置的 exporter（OTLP/HTTP、OTLP/gRPC、file、console）；SDK span **不被拦截**；host 产生的 session-title 元数据通过匹配的 forwarder 发出。

**DB 模式**  
触发：`chat.agentHost.otel.dbSpanExporter.enabled = true`（**隐式启用 OTel**）。  
`AgentHostOTelService` 在 `127.0.0.1` 上启动 `LocalOtlpHttpReceiver`（临时端口），SDK 指向该 loopback。每批 OTLP-JSON body 被解码并写入 `OTelSqliteStore`（`onSpans`）。如果**还配置了**外部 `otlpEndpoint`，receiver 将**原始** OTLP body fan-out 到 `OtlpHttpForwarder`（`onForward`），外部 collector 可同时接收 trace。

两种模式可同时使用：DB 落盘 + OTLP 转发，既能在 collector 中实时查看，又能事后查询原始数据。

### 3.3 信号路由：只有 trace 进入 Agent Host 管道

**只有 traces 进入 Agent Host loopback 和 SQLite**。Provider-native **logs 和 metrics 绕过 Agent Host，直接从 SDK 导出**。Agent Host **不接收或持久化** `/v1/logs` 或 `/v1/metrics`。审计或修改集成时，**权威来源是 provider/runtime 仓库**（如 `github/copilot-agent-runtime`），不是 VS Code 的 TypeScript 常量。

> **实测澄清：“只有 trace 进入 SQLite”不等于“库里只有 span”。**
> 落库结构是 `spans` + `span_attributes` + **`span_events`**（实测 5962 条，扩展库 21 条）：hook、sandbox 决策、
> `session.usage_info`（token_limit/current_tokens）、`gen_ai.client.operation.exception`（error_status_code/service_request_id）
> 都挂在 span 上，**属于 trace 的一部分**。所以“离线库查不到事件”是错的。
> 本项目 `LocalTraceImporter` 除 `spans` 外也读 `span_events`，目前只取 `github.copilot.hook.end` 还原 Hook 统计
> （实测导入 1976 条，会话页 hook 分组从 0 变 9），其余事件（`session.usage_info`、`sandbox.*`、
> `gen_ai.client.operation.exception`）需要新表才能干净承载，暂未导入。

### 3.4 设置与环境变量映射

| 设置 | 环境变量 |
|---|---|
| `chat.agentHost.otel.enabled` | `COPILOT_OTEL_ENABLED` |
| `chat.agentHost.otel.exporterType` | `COPILOT_OTEL_EXPORTER_TYPE` |
| `chat.agentHost.otel.otlpEndpoint` | `OTEL_EXPORTER_OTLP_ENDPOINT`（`COPILOT_OTEL_ENDPOINT` 优先） |
| `chat.agentHost.otel.captureContent` | `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` |
| `chat.agentHost.otel.outfile` | `COPILOT_OTEL_FILE_EXPORTER_PATH` |
| `chat.agentHost.otel.dbSpanExporter.enabled` | `COPILOT_OTEL_DB_SPAN_EXPORTER_ENABLED` |

**设置生效时机**：环境变量在 Agent Host **spawn 时绑定**（`buildAgentHostOTelEnv`），`IAgentHostOTelService` 构造时读取并缓存。**会话中途修改设置对已运行的 Agent Host 无效**，必须 **Reload Window** 或重启 VS Code。

### 3.5 资源标识与 trace context

Agent Host 设置 `service.namespace=vscode.agent-host`，各 producer 的 `service.name` 不同：

| Producer | `service.name` | 实测（本库） |
|---|---|---|
| Host session/title metadata | `vscode-agent-host` | 1245 |
| Copilot runtime | `github-copilot` | 11343 |
| Claude runtime | `claude-code` | 0（未使用） |
| Codex app-server | `codex-app-server` | 0（未使用） |

> **实测：Agent Host 把 resource attributes 写成 span attribute**，故离线也能分层——`service.namespace` 恒 `vscode.agent-host`（12588/12588）、
> `service.version` 是 runtime 版本（`1.0.103-unstable.*`）、`service.instance.id` 是 `copilot-otel-<pid>-<n>`（**含 PID**）、
> 另有 `server.address`（实测恒 `127.0.0.1`，是本地 provider 代理）、`server.port`、`process.executable.name/exit.code`、`enduser.pseudo.id`。
> **扩展库完全不存这些**，管线归因只能靠来源文件路径。

Host 发出**零时长** `vscode.agent_host.session` 锚点，将 W3C `traceparent`/`tracestate` 传递给 native runtime，使 provider-native trace **共享同一 trace id**，同时保留各自的 provider conversation 属性。

> **实测补充：host 合成 span 共四类**（官方文档只提 anchor 与 title_changed）——`vscode.agent_host.provider_timing` 1058（全部零时长）、
> `session` 41、`turn_timing` 57、`first_response` 43。它们的 `operation_name` 为 **NULL**，
> 按 `chat`/`execute_tool`/`invoke_agent`/`execute_hook` 四类过滤会整体漏掉。另有 `permission` 1780 与 `session.timing.{phase}` 约 4700 条同样 `operation_name IS NULL`。

### 3.6 内容捕获与 `captureContent: false`

默认不捕获 prompt、response、tool arguments、tool results。`captureContent: false` 时：

- **可用（实测）**：trace 拓扑、延迟、工具调用次数/类型/错误、token 用量（input/output/reasoning）、**资源属性**、
  命令退出码（`process.executable.name` / `process.exit.code`）、审批结果（`permission.kind/result`）、
  上下文用量（`session.usage_info` 的 `token_limit` / `current_tokens` / `messages_length`）、推理档位（`gen_ai.request.reasoning.level`）、
  压缩标记（`gen_ai.conversation.compacted`）、服务端耗时（`github.copilot.server_duration`）、runtime 费用（`github.copilot.cost`）、
  阶段耗时（`github.copilot.session.timing.*`、`vscode.agent_host.providerStage*/sendStage*`）、用户感知首响应（`*timeToFirstProgress`）。
- **不可用**：prompt/response 文本、tool arguments/results、file paths、commands、raw MCP server names、**session title 文本**
  （`vscode.agent_host.session.title_changed` span 仅在内容捕获启用时发出，**实测门控成立**：本机关闭时 0 条该 span、0 个内容键）。
- **实测更正：cache read/creation token 也不可用——但与 `captureContent` 无关**：Agent Host 侧两条键各 0 次、`cached_tokens` 列全 NULL。
- **实测补充：`github.copilot.context.skills` 与 `custom_agent_names` 是明文**（用户自建技能/代理名），只有 MCP server 名被哈希；
  `enduser.pseudo.id`、`service.instance.id`（含 PID）不受任何开关控制。

企业 managed 设置支持 `captureContent` 配合 `lockCaptureContent: true`，在组织层面**锁定关闭**内容捕获并阻止本地重新开启。

### 3.7 工具调用与缓存命中（`captureContent: false` 下）

**工具调用可以统计**：

| 维度 | 可用信号 | 实测校正 |
|---|---|---|
| 调用次数 | 按 `gen_ai.tool.name`、成功/失败聚合 | `copilot_chat.tool.call.count` 属 metrics，**不走本管道**；离线用 `spans`（实测 2470 条） |
| 延迟 | `execute_tool` span 时长 | 可用；另有 `github.copilot.server_duration`（825~332 855 ms） |
| 工具名 / 类型 | `gen_ai.tool.name`；`gen_ai.tool.type` | 外部工具名是 **SHA-256**（`8e6ae5f8…` 167 条）；**`tool.type` 实测全为 `function`，分不出 MCP** |
| 错误 | `error.type` | 取值含 `ToolError`/`ModelCallError`/`query`/`cancelled`/`denied`；实测工具错误率 64/2470 ≈ 2.6% |
| 调用拓扑 | `execute_tool` span 的父子关系 | **Agent Host 是真深树**，扩展管线基本没有父子关系 |
| MCP 工具 | 文档写 `mcp_server_name_hash`、`mcp_tool_name` | **两键实测都不存在**；实际是 `context.mcp_server_names`（哈希数组）+ `external_tool.name`/`permission.tool_name`（哈希）；且 `external_tool {sha}` 与 `execute_tool {sha}` **成对重复**，按 `tool.call.id` 去重 |
| 命令 | 需内容捕获 | **退出码免费可得**：`process.exit.code`（0/1/2 = 829/69/3） |
| 审批 | （官方文档未列） | **`permission` span 1780 条**：kind = read/shell/write/url/custom-tool，result = approved/denied-interactively-by-user |

**缓存命中：扩展管线可以统计，Agent Host 目前不行。**

| 管线 | `cache_read` | `cache_creation` | 实测 |
|---|---|---|---|
| Copilot Chat | **可用**（chat 3245 次） | 0 次 | 总体命中 **99.03%**，逐条 `cached ≤ input` → **`input_tokens` 已含缓存**，分母直接用它 |
| Agent Host | **0 次** | 0 次 | `cached_tokens` 全 NULL；命中率必然为空，属**数据源缺失**而非未命中 |

`gen_ai.usage.input_tokens` 的 provider 语义差异（Anthropic 排他 vs OpenAI 含缓存）**已实测确认**：扩展管线走 OpenAI 兼容 `messages` API，
属**含缓存**口径；只有 Anthropic/Claude 类 provider 需要 `input + cache_read + cache_creation`。不要跨 provider 直接比较命中率。


## 4. Local Copilot Chat OTel 管道

### 4.1 定位与多代理架构

Local Copilot Chat 是**扩展宿主内独立、用户可见的管道**，配置前缀 `github.copilot.chat.otel.*`，使用 `IOTelService`。扩展有**四条代理执行路径**，各自采用不同的 OTel 策略：

| Agent | 进程模型 | OTel 策略 | 关键路径 |
|---|---|---|---|
| **Foreground**（`toolCallingLoop`） | 扩展宿主 | 直接 `IOTelService` spans | `extensions/copilot/src/extension/intents/node/toolCallingLoop.ts` |
| **Copilot CLI in-process** | 扩展宿主（同进程） | **Bridge SpanProcessor**：SDK 原生创建 spans，bridge 转发到 debug panel | `extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotCliBridgeSpanProcessor.ts` |
| **Copilot CLI terminal** | 独立终端进程 | 转发 OTel 环境变量 | `extensions/copilot/src/extension/chatSessions/copilotcli/node/copilotCLITerminalIntegration.ts` |
| **Claude Code** | 子进程（Node fork） | **从 SDK 消息合成 spans**：拦截 Claude SDK 消息流，LLM 调用通过本地 HTTP 代理产生标准 `chat` spans | `extensions/copilot/src/extension/chatSessions/claude/common/claudeMessageDispatch.ts`；`claudeLanguageModelServer.ts` |

**为什么不对称？** CLI SDK 在进程内运行，拥有完整 trace 层级（子代理、权限、hooks），bridge 可直接捕获；Claude 作为独立进程运行，内部 spans 不可访问，扩展通过翻译 SDK 消息和代理模型 API 来合成 spans。

### 4.5 属性命名空间与双重发出策略

扩展发出的 spans 上共存**三个命名空间**：

| 命名空间 | 用途 | 状态 |
|---|---|---|
| `gen_ai.*` | OTel GenAI 语义约定；存在标准键时使用 | **规范** |
| `github.copilot.*` | Copilot 专用供应商命名空间 | **首选 — 新属性放这里** |
| `copilot_chat.*` | 原始 VS Code 专用命名空间；部分键保留向后兼容 | **旧版 — 继续发出；不要新增键** |

**双重发出规则**：当把现有 `copilot_chat.*` 属性重命名为 `github.copilot.*` 等价项时（如 `copilot_chat.repo.*` → `github.copilot.git.*`，`gen_ai.usage.reasoning_tokens` → `gen_ai.usage.reasoning.output_tokens`），**无限期双重发出两个键**；下游读取方（Agent Debug Log、Chronicle、SQLite span store、OTLP collector）可能依赖旧版键。**没有终止日期**。敏感标识符（如 MCP server 名称）用 `hashTelemetryValue` 无条件发出哈希；原始值仅在 `captureContent` 启用时发出。

### 4.6 工具调用与缓存命中（`captureContent: false` 下）

与 Agent Host 一致的部分：**工具调用次数、延迟、工具名/类型、错误、拓扑可统计**；缓存读取 token（`gen_ai.usage.cache_read.input_tokens`）可统计，独立于 `captureContent`。不可用的是 tool arguments/results、commands、file paths、raw MCP server names。

**实测三点差异（必须记住）**：

1. **扩展管线的拓扑几乎是平的**：3285 个 span 里 3275 个 `parent_span_id IS NULL` 且各自独占 trace，只有子代理 `runSubagent` 一条链路成树。
   会话页 Trace 拓扑对纯扩展来源只能靠 `conversation.id` + 时间区间重建层级。
2. **`cache_creation.input_tokens` 0 次**（两条管线都是），所以“缓存写入按缓存写入价计费”分支目前不会被触发。
   `cache_read` 只有扩展管线有，实测总体命中 99.03%，且 `input_tokens` **已含**缓存 → 命中率分母直接用 `input_tokens`。
3. **`gen_ai.tool.type` 分不出 MCP**（实测全 `function`）；外部工具名在两条管线都以 **SHA-256** 出现，
   Agent Host 还会为同一次调用发出成对的 `external_tool {sha}` + `execute_tool {sha}` span。

### 4.7 与 Agent Host 的互补关系

| 场景 | 配置 |
|---|---|
| 只使用 Local Copilot Chat（前台/内联） | 仅 `github.copilot.chat.otel.*` |
| 使用 Agent Host 会话（Copilot/Claude/Codex 通过 Agent Host） | 仅 `chat.agentHost.otel.*` |
| 两者都使用 | **两个都配**，但后端按 `service.name` / `service.namespace` 或执行表面标签**分开聚合** |

**不是重复统计同一批数据**，而是按执行表面互补。企业托管设置（`telemetry` block）可以同时作用于两个表面，但**数据来源仍是两条独立管道**。

## 7. 排查清单

| 现象 | 检查 |
|---|---|
| Agent Host 完全没有数据 | `chat.agentHost.otel.enabled` 是否为 `true`；是否 Insiders / 非 stable 构建；`chat.agentHost.enabled` 是否为 `true`；endpoint/exporter 是否正确；**是否已 reload window / 重启** |
| Agent Host 有 trace 但无 metrics | Agent Host 管道**只处理 trace**；metrics 由 provider 直接导出，确认外部端点和 provider 是否发出 |
| **实测**：导入的会话结果卡片为空 | 离线 SQLite **不含 metrics**（`/v1/metrics` 被 receiver 丢弃），`import-local` 无论怎么改都不可能有编辑指标；结果指标只能等在线 OTLP |
| **实测**：在线有 spans 但 outcome 卡片仍空 | 结果指标的 datapoint **不带会话 ID**，只能靠「窗口内唯一 chat 会话」归属；同窗口开第二个会话后就不再进会话卡片（Dashboard 仍有），这是数据源限制 |
| DB 模式下外部 collector 收不到 trace | 外部端点需为 **OTLP/HTTP JSON**；protobuf/gRPC 外部协议下 trace 只留在 SQLite |
| 工具调用有但无参数/结果 | `captureContent = false`，**预期行为** |
| 缓存字段为 0 或缺失 | 是否多轮稳定前缀；provider 是否报告；`input_tokens` 语义按 provider 确认；Cache Explorer 交叉验证 |
| 中途改 Agent Host 设置不生效 | 必须 reload window 或重启 VS Code；Agent Host 构造时缓存环境变量 |
| AHP Telemetry 订阅收不到历史数据 | Telemetry 通道**无状态、不重放**；只能接收实时边缘；需要历史请查 Agent Host SQLite |
| Copilot Chat 与 Agent Host 数据“对不上” | 两条管道独立，不应直接合并；按 `service.name` 或执行表面标签分开聚合 |
| Claude 没有 `claude_code.*` spans | `chat.agentHost.otel.*` **不**自动开启 Claude 的 native OTel；需单独配置 Claude standalone OTel 设置 |
| **实测**：缓存命中率只在部分会话有值 | Agent Host 不发 cache token（数据源缺失）；只有 Copilot Chat 来源能算命中率，UI 不要渲染成 0% |
| **实测**：`execute_hook` 一条都查不到 | 两条管线都不发该 span；hook 统计要读 `span_events`（本项目导入路径目前完全没读） |
| **实测**：离线库分不出来源管线 | 扩展库不存 resource attributes，只能按**文件路径**归因；`service.namespace` 只在 Agent Host 库里有 |
| **实测**：扩展库体积异常大 | `captureContent=true` 时 `gen_ai.input.messages` 单键即占 83%（实测 3.04 GB / 3.63 GB），关闭后旧行不回收 |
| **实测**：模型厂商判错 | 别用 `gen_ai.provider.name`（`github`/`openai` 都表示协议）；Agent Host 看模型名前缀，扩展看 `server.address` |
| **实测**：会话总量翻倍 | `invoke_agent` 的 usage 是会话汇总，与 `chat` 合计逐值相等；聚合必须限定 `operation_name='chat'` |
| **实测**：Agent Host 端到端耗时异常 | 先查 `permission` span（最长 14.3 小时人审等待），与模型无关 |
